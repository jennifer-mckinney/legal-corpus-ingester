# VCR drift canary

## Purpose

VCR cassettes are snapshots of live upstream HTTP responses recorded at
ingest time and committed to the repo. They let integration tests run
offline and deterministically. Over time, upstream sources restructure
URLs, change response schemas, add or remove XML elements, or alter
headers. When that happens, the cassettes in the repo no longer match what
a fresh fetch would produce. The drift canary exists to surface that
divergence before it causes silent corpus corruption.

The canary re-records all cassettes against live sources on a weekly
schedule, diffs the results against the committed versions, and escalates
when anything changed.

## Trigger

GitHub Actions cron `0 4 * * 0` - Sunday 4 AM UTC. The weekly cadence
balances detection latency against the cost of a live fetch run. It also
runs on `workflow_dispatch` so any team member can trigger it manually
before cutting a release or after a source announces a schema change.

## What it does

The workflow runs these steps in order (`.github/workflows/vcr-drift.yml`).

**1. Stash baseline and delete.** The committed `tests/fixtures/cassettes/`
tree is copied to `$RUNNER_TEMP/vcr-baseline` (a fresh per-run directory, not
shared `/tmp`), then every committed `*.yaml` cassette is deleted from the
working tree. Deleting first means only cassettes a test actually re-records
this run exist on the current side. A cassette no test re-records shows up as
"baseline only" instead of being compared with itself.

**2. Re-record in rewrite mode.** The integration suite runs with
`pytest tests/integration/ --record-mode=rewrite -v -rs` plus a JUnit XML
report. `--record-mode` is the `pytest-recording` flag. `rewrite` discards each cassette before recording, so the
file holds only fresh interactions; `all` would load the committed
interactions and append to them, hiding body drift. A failing fetch makes
pytest exit non-zero and the step fails.

**3. Skip guard.** `scripts/vcr_skip_guard.py` reads the JUnit XML and fails
if any test was skipped or if zero tests ran. A skipped test records nothing,
so its endpoint went unchecked while pytest still exits 0.

**4. Diff and report.** `scripts/vcr_drift_report.py` compares the baseline
against the freshly recorded cassettes (`interactions[*].request.uri` and
`interactions[*].response.body.string`), writes `drift-report.md`, and the
step records its exit code as an output.

## What it produces

**Artifact.** `vcr-drift-report-<run_id>` is uploaded on every run
(`if: always()`). It contains `drift-report.md` and the re-recorded
cassettes, so a truncated report still has full detail one click away.

**Issue.** If any step fails, the final step opens a GitHub issue (labels
`corpus-drift`, `needs-review`). No issue opens when every step passes. Its title, labels
and body come from the outcome table `ISSUE_OUTCOMES` in
`scripts/vcr_drift_report.py`; the block below is that table's output, and
a test fails if the two differ:

**Dedupe.** If a `corpus-drift` issue is already open, the workflow comments
on it (with the title in bold) instead of opening a new issue each Sunday.

**Size caps.** The report is capped at 60000 bytes on whole-block UTF-8
boundaries, and the issue body at 64000 bytes (`head -c`), under GitHub's
65536-character limit. Truncated reports point at the run and artifact.

## How to read the drift report

| Bucket | Meaning |
|--------|---------|
| Unchanged | Cassette matches the committed one; upstream is stable. |
| Changed | At least one interaction differs; inspect carefully. |
| Baseline only (not re-recorded this run) | No test re-recorded it this run (skipped, renamed, or made no request). Check the re-record log. It does not by itself mean the endpoint is gone. |
| Current only (new endpoint) | New cassette with no committed counterpart. |
| Parse errors | A cassette could not be parsed or had nothing to compare. |

When inspecting a "Changed" cassette:

- URI drift in `interactions[*].request.uri` indicates a URL restructuring
  on the upstream source. All downstream config pointing at the old URI
  needs updating.
- Body structure drift in `interactions[*].response.body.string` indicates
  a schema change (different XML element names, moved fields, altered
  envelope format). The cleaner for that source likely needs updating too.
- Header-only changes (charset additions, caching headers, server version
  strings) are typically noise. Response Set-Cookie and auth headers are
  scrubbed at record time.

## Escalation

**Drift detected.** A human reviews the report and decides whether the
upstream change is compatible with the current cleaner or needs a schema
update. Until the issue is closed, the affected source is considered
unreliable.

**Severe drift.** If the upstream format changed in a way the current
cleaner cannot handle (for example, the GDPR XML envelope switched from
AkomaNtoso to a proprietary schema), the maintainer marks the source as
publish-blocked and updates `ALERTS.md` with the source name, the detected
change, and the date. The publish pipeline treats a publish-blocked source
as a hard failure per HR5.

**No drift.** The artifact is uploaded, no issue is opened, the workflow
exits 0.

## Failure mode

A canary failure always alerts. If the re-record step fails (an upstream
returned 4xx/5xx, or a test errored), or the skip guard fails (a test was
skipped or zero tests ran), the report step does not run and the issue step
opens or comments with the `broken` outcome from the table above, linking
the failed run. The cassettes in the working tree are then in an undefined state.
Open the run log to tell "upstream is down" (fetch failure) from "a test was
skipped" (the guard names each skipped test on stderr).

## Where it runs

The job runs on GitHub-hosted `ubuntu-latest` (ADR-016). The re-record step
makes live HTTP calls to each source (EUR-Lex, Congress.gov and the others),
so those requests originate from GitHub's infrastructure. The re-recorded
cassettes leave the runner only as the run artifact.

## Relationship to ALERTS.md

The drift canary is the automated tripwire. `ALERTS.md` is the human
escalation record. When the canary fires and a human confirms the drift
constitutes a schema change, they update `ALERTS.md` and set publish to
blocked for the affected source. The issue opened by the canary references
`ALERTS.md` as the escalation target.

## Running manually

Use a private temp directory (not a shared `/tmp` path).

```bash
export VCR_TMP="$(mktemp -d)"
cp -R tests/fixtures/cassettes "$VCR_TMP/vcr-baseline"
find tests/fixtures/cassettes -type f -name '*.yaml' -delete
source .venv/bin/activate
pytest tests/integration/ --record-mode=rewrite -v -rs --junitxml="$VCR_TMP/vcr-junit.xml"
python scripts/vcr_skip_guard.py "$VCR_TMP/vcr-junit.xml"
python scripts/vcr_drift_report.py --baseline "$VCR_TMP/vcr-baseline" \
  --current tests/fixtures/cassettes --output drift-report.md
cat drift-report.md
```

Restore committed cassettes afterward with
`git checkout -- tests/fixtures/cassettes/` so the working tree does not
contain live-recorded cassettes that differ from the committed baseline.
