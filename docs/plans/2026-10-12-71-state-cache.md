## 1. Goal

Since ADR-016, the state that refresh and health keep under `~/.local/state/legal-corpus-ingester/` starts empty on every GitHub-hosted job. The goal is for that directory to survive from one run to the next through `actions/cache`. The design must never confuse "no state was restored" with "state says nothing changed" (the success-path defect class named in #71). It also needs an explicit seed step, so the first record can be written on purpose and the `--require-state` guard kept by the owner's ruling on PR #69 doesn't leave refresh red forever.

### Acceptance criteria

1. `refresh.yml` restores the state directory before any step reads it and saves it under a new, run-unique key after the record step. `health.yml` only restores it and never saves.
2. The reader reports one of four states, and the workflow log shows which one:
   - `absent`: no cache entry was restored **and** the state root is empty (missing, or a directory with no entries at all). The run is red (exit 2, `EXIT_NO_STATE`, kept) and is never reported as "unchanged".
   - `seeded`: a valid seed marker exists, a cache entry was restored, and no record file exists yet. The first publish counts as a change and is announced exactly once.
   - `present`: a valid marker and a record that passes the same schema rule as `read_state` both exist. The normal comparison runs.
   - `invalid`: anything else, with a reason (§4). Exit 1, loud, never saved.
3. These are `invalid`, never `absent`: a non-empty root with no marker (whatever restored it, including a partly extracted archive, §9); a marker on a run where no cache entry was restored; a restored entry with no marker; a malformed marker, record or checkpoint.
4. A seed path exists. It runs only on the default branch, refuses unless the state is `absent` (so never over restored state or over unexplained files in the root), and saves a cache entry that the next refresh and health runs restore.
5. A save never writes an entry that would shadow good state. The save runs only when the post-run verify step reports `seeded` or `present` (an allowlist), never on a cancelled run, and never from a ref other than the default branch.
6. Every state-touching job has a least-privilege `permissions:` block (`health.yml` has none today), and all state writers share one `concurrency:` group.
7. Red tests in §10 are committed first and fail for the stated reason; they turn green with the implementation; CI is green on the exact tip.
8. The ADR-016 "Consequences" paragraph and the `refresh.yml` comment on `--require-state` are updated, so neither says persistence is undecided. Which document records the decision is OPEN Q6.

## 3. Key scheme

```yaml
key:          ingester-state-v1-${{ github.ref_name }}-${{ github.run_id }}-${{ github.run_attempt }}
restore-keys: |
  ingester-state-v1-${{ github.ref_name }}-
  ingester-state-v1-${{ github.event.repository.default_branch }}-
path:         ~/.local/state/legal-corpus-ingester
```

The key has to be different on every save, because cache entries are immutable. GitHub's docs say: "You cannot change the contents of an existing cache. Instead, you can create a new cache with a new key" [D1]. The actions/cache tips page gives the same recipe: a key unique to each run, such as `github.run_id`, plus `restore-keys` to fetch the nearest entry [D4]. A constant key would be written once and then never change, which would freeze the first record forever. That is the failure #71 warns about.

- `run_id` makes the key unique per run. `run_attempt` makes a re-run of the same run unique too. Without it, a re-run would try to save an existing key, and [D3] does not document what that does.
- **The `restore-keys` prefix** fetches the newest entry: "If there are multiple partial matches for a restore key, the action returns the most recently created cache" [D1]. A partial match sets `cache-hit` to `false` and puts the restored key in `cache-matched-key` [D2]. So the reader is given `cache-matched-key`, never `cache-hit`.
- `ref_name` plus a fallback to the default branch: a run can restore caches from its own branch and from the default branch, but not the other way round. A cache created by a pull-request run is scoped to `refs/pull/.../merge` and can only be restored by re-runs of that PR [D1]. Saves are gated to the default branch (§5), so in practice every entry is `ingester-state-v1-main-…`.
- **The two `restore-keys` lines play different roles.** The first line, `ingester-state-v1-${{ github.ref_name }}-`, is a prefix of the save `key` on every ref, because both start with the same `ref_name`. The second line, `ingester-state-v1-${{ github.event.repository.default_branch }}-`, is the default-branch prefix. It is a prefix of the save key only when the run is on the default branch, where it equals the first line. On any other branch it is deliberately **not** a prefix of that run's key: it exists so a branch dispatch can read main's state without being able to write any. T-W2 checks both cases.
- `v1` is a schema segment. A future change to the marker or record format bumps it to `v2`, so old entries can never be restored into new code.
- **The path must be the same literal string in both workflows.** The cache version is a hash of the compression method and the `path` [D5], so if `refresh.yml` and `health.yml` spell the path differently, health misses on every run. A test pins this (T-W3). `~` is supported in `path` (the README examples use `~/.npm`, `~/.cache/pip` [D5]). The `${XDG_STATE_HOME:-…}` shell form cannot be used in a `with:` input, so the steps pass explicit `--state-file` and `--state-dir` values derived from the same root, and `XDG_STATE_HOME` is never relied on.

## 4. State layout and reader states

```
~/.local/state/legal-corpus-ingester/
  store.json                    # NEW marker: {"schema": 1, "seeded_at": "<UTC ISO>", "seeded_by_run": "<run_id>"}
  last-published-bundle.json    # existing record (detect_bundle_change.py)
  state/<source>.checkpoint.json  # existing checkpoints (health_check.py, ingester status)
```

`classify(root, restored_key)` takes the matched key the workflow passes in (`--restored-key "${{ steps.restore.outputs.cache-matched-key }}"`, which is empty on a miss):

"Empty root" means the root does not exist, or is a directory with no entries at all. Any file, directory, symlink or dotfile counts as contents, including a leftover `*.tmp`. Rows are evaluated top to bottom; the first match wins.

| # | `restored_key` | Root contents | Result (`reason`) | detect (`--require-state`) | health_check |
|---|---|---|---|---|---|
| 1 | empty | empty | `ABSENT` (miss or eviction) | exit 2, nothing written to `GITHUB_OUTPUT`, `::error` naming the reseed procedure | exit 5 (or a warning while unwired, OPEN Q2) |
| 2 | empty | non-empty, no `store.json` | `INVALID` (`untrusted-contents`): files of unknown origin, for example a partly extracted archive (§9) or a stray directory on a self-hosted runner | exit 1 | fail |
| 3 | empty | `store.json` present | `INVALID` (`marker-without-restore`): state of unknown origin | exit 1 | fail |
| 4 | non-empty | no `store.json` (empty or not) | `INVALID` (`restore-without-marker`): a cache entry without a marker | exit 1 | fail |
| 5 | any | `store.json` unreadable, not JSON, wrong `schema`, a directory or a symlink | `INVALID` (`bad-marker`) | exit 1 | fail |
| 6 | any | `last-published-bundle.json` exists but fails `validate_record` (unreadable, not JSON, not an object, missing `version` or `fingerprint`, a directory or a symlink) | `INVALID` (`bad-record`) | exit 1 (the existing `BundleError` path, same rule) | fail |
| 7 | any | a `state/*.checkpoint.json` fails `checkpoint_problem` | `INVALID` (`bad-checkpoint`) | exit 1 | exit 4 (unchanged checkpoint-problem result) |
| 8 | non-empty | valid marker, no record file | `SEEDED` | `changed=true`, `reason=first-record` | normal never-run rules |
| 9 | non-empty | valid marker, valid record | `PRESENT` | normal compare | normal rules |

Four properties follow. `ABSENT` can never be read as "unchanged", and it means an empty root, not merely a missing marker: unexplained files are `INVALID`, so `seed` (which needs `ABSENT`) cannot stamp a marker onto them. `SEEDED` is the only way a first publish gets announced, and it happens because someone seeded on purpose, not because state was lost; a malformed record is never mistaken for "no record yet". `PRESENT` uses `validate_record`, the same function `read_state` uses, so a record that would make detect fail can never be classified `PRESENT` and therefore can never be saved (§5 step 8 only saves `seeded` or `present`). The cross-check against `restored_key` stops a stray directory on the runner (or a future self-hosted runner) from passing as restored state.

When no flag is given, the current behaviour stays the same (`test_without_the_flag_first_publish_is_still_a_change`). The new rules apply only under `--require-state` / `--restored-key`, which the workflows always pass (T-W4).

## 5. Order in `refresh.yml`, and whether to save on failure

1. `actions/checkout` (persist-credentials: false, as now)
2. `actions/cache/restore` (`id: state_restore`), with `key` and `restore-keys` from §3
3. Preflight, setup-python, Install (unchanged)
4. `python scripts/state_store.py check --restored-key … --github-output "$GITHUB_OUTPUT"` (`id: state_check`). It logs the state and matched key to `$GITHUB_STEP_SUMMARY`. Exit 2 or 1 stops the job here with a clear message, before refresh spends its fetch budget.
5. `ingester refresh --all` (exit 3 until G2, unchanged)
6. Detect (`--require-state --restored-key …`), then Announce, then Record (unchanged order; Record still runs only after a successful announce)
7. `scripts/state_store.py check` again (`id: state_verify`), so a corrupt record is never saved. This step carries `if: ${{ !cancelled() }}`. Without it the step would take the implicit `success()` and be skipped whenever an earlier step failed; `state_verify.outputs.state` would then be empty and the save in step 8 would never run, which would silently disable the save-on-failure decision (Q3). T-W12 pins this `if:`.
8. `actions/cache/save`, with:
   ```yaml
   if: >-
     !cancelled()
     && github.ref == format('refs/heads/{0}', github.event.repository.default_branch)
     && (steps.state_verify.outputs.state == 'seeded'
         || steps.state_verify.outputs.state == 'present')
   with:
     key: ${{ steps.state_restore.outputs.cache-primary-key }}
   ```
   The state condition is an allowlist rather than "not empty and not absent". `check` writes no `state=` on `invalid` (§2), so an invalid store already gives an empty output, but the allowlist also stays closed if a future status is added.
9. Upload health report (unchanged)

**Proposed decision: save on failure, but not on cancellation** (`!cancelled()`, not `always()`). OPEN Q3 lists the alternatives.

- Saving after a failure is safe because the record is only ever advanced after a successful announce, and `write_state` / `CheckpointStore.save` replace files atomically. Whatever is on disk at step 8 is a consistent "last announced" view. Saving it unchanged just refreshes the entry's access time. The vendor documents this pattern: `actions/cache/save` with `always()` [D3].
- Skipping a save after a failure loses nothing that was announced. It does lose checkpoints a partly successful wired refresh wrote, so the next run starts from older checkpoints.
- Cancellation is excluded because a cancel can land between Announce and Record. Saving in that case gives a duplicate announcement next week, which is loud. Not saving gives the same result. `!cancelled()` keeps the rule simple.
- Saving when the state is `absent` or `invalid` would create an entry that is newer than the good one. `restore-keys` would then pick it [D1] and **shadow** the good state. The `seeded`/`present` allowlist and the verify step exist for exactly this reason. A malformed record classifies `invalid` (§4 row 6), so it is never saved.

`health.yml` order: checkout, restore (same `path`, same `restore-keys`, `key` set to a value that never matches such as `ingester-state-v1-read-${{ github.run_id }}`), setup-python, install, `health_check.py --state-dir <root>/state --restored-key …`, `ingester status`, upload. It has no save step. Health is the "low-trust" reader that [D1] says should use restore-only.

## 6. Eviction and its side effect

Entries "not accessed in over 7 days" are evicted, within a 10 GB repository cap by default [D1]. Refresh runs weekly (Sunday 03:00 UTC), right on that boundary. Health runs nightly and restores the newest entry, which counts as an access and keeps that entry alive. If health is disabled for more than 7 days and refresh does not run, the state is evicted. The next refresh then classifies `ABSENT`, goes red with exit 2, and the operator reseeds (§7). The cost is at most one duplicate announcement and never a silent miss. Each entry is a few KB, so the 10 GB cap is not a concern. Older entries age out on their own 7-day clock (OPEN Q4 covers active pruning).

## 7. The seed step

- **Who:** the owner, or an operator acting on the owner's instruction, by a manual `workflow_dispatch` on the default branch. It never runs automatically. An automatic seed when the state is `ABSENT` would recreate the silent "never run equals first publish" behaviour that #71 exists to prevent (OPEN Q1, option c).
- **When:** once, right after the implementation PR merges, and before the next 03:00 UTC health run if Q2 picks "red". After that, only to recover from an `ABSENT` red run (eviction, or a `v2` schema bump), and only after `gh cache list --key ingester-state-v1-` confirms no entry exists. An `ABSENT` caused by a cache outage (§9, outcome A) is fixed by a re-run, not a reseed.
- **What:** restore (same key scheme). Then `state_store.py seed --restored-key …`, which refuses with exit 1 unless the state classifies `ABSENT`, so it cannot overwrite live state and cause a duplicate announcement. Because `ABSENT` needs an empty root (§4), seed also refuses a root that holds files but no marker, rather than blessing contents of unknown origin. It then writes `store.json` and saves under `ingester-state-v1-main-<run_id>-<attempt>`.
- **Proposed placement (OPEN Q1, option a):** a `seed` job inside `refresh.yml`, selected by a boolean `workflow_dispatch` input `seed_state`. Its condition is `if: inputs.seed_state && github.ref == format('refs/heads/{0}', github.event.repository.default_branch)`, and the `refresh` job gets `if: ${{ !inputs.seed_state }}`. Both jobs sit under the workflow's existing `concurrency: refresh` group, so a seed can never race a refresh.
- **Check after seeding:** `gh cache list --key ingester-state-v1-` shows the new entry, and the next health run's summary reads `state=seeded`.

## 8. Concurrency and permissions

- **Concurrency:** keep `refresh.yml`'s workflow-level `group: refresh`, `cancel-in-progress: false`; the seed job inherits it because it lives in the same workflow (Q1a). If Q1 picks a separate workflow, that workflow must join the same group name. A single group allows one running run and one pending run; a third queued run replaces the pending one. With a weekly schedule plus manual dispatches, that is acceptable. `health.yml` needs no group because it never writes. A health run that restores while a refresh is saving gets the previous entry, which is consistent but one run old.
- **Permissions:** cache restore and save use the runner's Actions runtime token, not `GITHUB_TOKEN` scopes. The actions/cache README asks for no `permissions:` entry [D5], and "read-only" cache access degrades to a warning, never a failure [D5]. The implementer confirms this on the first dispatch, which is test T-R2. Resulting blocks:
  - `refresh.yml`: unchanged (`contents: read`, `issues: write`); the `seed` job sets `permissions: contents: read`.
  - `health.yml`: add `permissions: contents: read`. Today it has no block and inherits the repository default.
  - `actions: write` is needed only for `gh cache delete` [D4], which is OPEN Q4b. `actions: read` is needed only for a post-save `gh cache list` lookup, which is OPEN Q7b.
- **Pinning:** `actions/cache/restore` and `actions/cache/save` are pinned by full SHA with a version comment, matching the other actions. The latest release on 2026-10-11 was `v6.1.0` → `55cc8345863c7cc4c66a329aec7e433d2d1c52a9` (`gh api repos/actions/cache/commits/v6.1.0`). The implementer re-checks this at implementation time.

## 9. Failure modes and observability

| Failure | Detected by | Result |
|---|---|---|
| Cache miss, eviction, or first run before a seed | `classify` gives `ABSENT` | refresh red with exit 2 and `::error` "state cache miss: no entry for prefix ingester-state-v1-…; reseed via …"; health exit 5 or a warning (Q2) |
| Restored entry with no marker, or files in the root with no marker | `classify` gives `INVALID` (§4 rows 2 and 4) | exit 1; not saved; `seed` refuses |
| Corrupt marker, record or checkpoint | `classify` gives `INVALID` (§4 rows 5 to 7), sharing `validate_record` with `read_state` and `checkpoint_problem` with health | exit 1 (health keeps exit 4 for checkpoints); not saved |
| `path` differs between workflows | T-W3 in CI; at runtime a miss classifies `ABSENT` | red, never silent |
| Cache service outage during restore, outcome A: degrades to a miss (restore step green) | `classify` gives `ABSENT` (empty root) or `INVALID` (`untrusted-contents`, a partly extracted archive) | see "Cache service outage" below |
| Cache service outage during restore, outcome B: restore step red | the step itself (`setFailed`) | see "Cache service outage" below |
| Cache service outage during save | nothing in the step result: save never fails the step and has no outputs (see below) | the entry is not written; the next run restores the previous entry. A second announcement of the same bundle is possible, and it is loud |
| Seed run while state exists | `seed` refuses (exit 1) | no overwrite |
| Branch dispatch | save gated to the default branch | branch runs never write state (Q5) |
| Cancelled between Announce and Record | `!cancelled()` gate | one duplicate announcement next run |

### Cache service outage: the two red outcomes in v6.1.0

Checked against the actions/cache source at the pinned SHA `55cc8345863c7cc4c66a329aec7e433d2d1c52a9` (v6.1.0) [S1]. `actions/cache/restore` runs `restoreImpl` with a `NullStateProvider`, which writes `cache-matched-key` as a step output only when a key was matched (`src/restoreImpl.ts` lines 111-115, `src/stateProvider.ts` lines 35-39).

**Outcome A: the outage degrades to a miss and the restore step is green.** Three code paths lead here:
- The cache feature is unavailable: `src/restoreImpl.ts` lines 17-19 set `cache-hit=false` and return. `isCacheFeatureAvailable` (`src/utils/actionUtils.ts` lines 69-86) logs the warning "An internal error has occurred in cache backend…". `cache.isFeatureAvailable` checks only that the service URL environment variables are set (`dist/restore-only/index.js` line 94334).
- The service fails during lookup or download: the `restoreCacheV2` `catch` (`dist/restore-only/index.js` lines 94514-94530) rethrows only `ValidationError`. Any other error is logged, as `core.error` for HTTP 5xx and as a warning otherwise ("Failed to restore: …"), and the function returns `undefined`.
- `src/restoreImpl.ts` lines 53-68 then treat `undefined` as a miss: `core.info("Cache not found…")` and return. The step fails only when `fail-on-cache-miss` is set, which this plan does not use.

In every case `cache-matched-key` is empty. The archive is extracted inside that same `try` block (line 94510), so an extract that fails part-way also lands here and may leave files in the root.
- **refresh:** `state_check` classifies `ABSENT` when the root is empty, which gives exit 2 and an `::error` saying the miss may be a cache outage and pointing at the restore step's annotations. It classifies `INVALID` (`untrusted-contents`, exit 1) when a partial extract left files. The job is red either way and stops before the fetch budget is spent. `state_verify` still runs (`!cancelled()`). It reports `absent`, or nothing when the state is invalid, so the allowlist in step 8 skips the save and the good entry is never shadowed.
- **health:** `health_check.py` classifies the same way. `ABSENT` gives exit 5, or a warning while unwired (Q2); `INVALID` fails. The upload step still runs (`if: always()`).
- Recovery: re-run once the cache service is back. Do **not** reseed, because the good entry still exists and a reseed would announce the current bundle again. The `::error` text says so, and §7's reseed procedure says "only after confirming with `gh cache list` that no entry exists".

**Outcome B: the restore step is red.** Any exception that reaches the `catch` in `src/restoreImpl.ts` lines 86-88 calls `core.setFailed(message)`. That includes a rethrown `ValidationError` from `restoreCacheV2` and any error thrown outside it.
- **refresh:** the restore step is red. `state_check`, refresh, detect, announce and record are all skipped by the implicit `success()`. `state_verify` runs (`!cancelled()`) on an empty root and reports `absent`, so the save is skipped. The upload step runs (`if: always()`). The job is red, nothing is announced and nothing is saved.
- **health:** the restore step is red, `health_check.py` and `ingester status` are skipped, the upload runs, and the job is red.
- Recovery: re-run. If the error is a `ValidationError`, the key template is wrong; T-W2 exists to catch that in CI first.

Neither outcome can produce `changed=false` or a save of empty state. In outcome A the run is red because the reader goes red; in outcome B it is red because the restore step does.

**Save.** `actions/cache/save` never fails its step. `src/saveImpl.ts` line 15 turns uncaught exceptions into warnings, and lines 22-24 return silently when the feature is unavailable. Lines 46-55 skip the save as a no-op when the key equals a restored key, and the `catch` at lines 75-76 logs a warning. The only positive signal is the `core.info` line "Cache saved with key: …" at lines 72-74, logged when `cacheId != -1`. The save action has no outputs [D3].

### Run summary

Every run writes `state=<absent|seeded|present|invalid: reason>`, `restored-key=<key or none>` and `save-attempted-key=<key or skipped: reason>` to `$GITHUB_STEP_SUMMARY`. A skipped save says why, so a save that silently does nothing cannot happen. The health report gains one line naming the state.

**Proposed: report `save-attempted-key`, not `saved-key`.** The save step exposes no output and swallows every error as a warning (above), so the workflow cannot honestly claim "saved". It can only claim "attempted with key K". The proof that the save landed comes from the next consumer. The next health run, within 24 hours, logs `restored-key=K`, and if that key is older than the latest refresh run, the save failed. Adding a post-save lookup (`gh cache list --key K` with exit-code check) would give a same-run `saved-key`, but it needs `actions: read` on the refresh job and a `GH_TOKEN`, which is custom verification machinery on top of a vendor action. The alternative is OPEN Q7.

## 10. TDD test list (red first)

The test-author commits these before any implementation. Every test names the defect it would catch.

**Unit: `tests/unit/test_state_store.py` (new)**
- T-U1: `ABSENT` only for a truly empty root with empty `restored_key`: both a missing root and an existing directory with no entries. A root holding any single entry (a stray file, a `*.tmp`, a dotfile, an empty `state/` directory, a symlink) and no marker gives `INVALID` (`untrusted-contents`), not `ABSENT`.
- T-U2: marker, no record, non-empty key gives `SEEDED`.
- T-U3: marker plus a valid record plus key gives `PRESENT`.
- T-U3b: malformed record gives `INVALID` (`bad-record`), never `PRESENT` or `SEEDED`, for each of: not JSON, a JSON array, an object missing `version`, an object missing `fingerprint`, a directory, a symlink, an unreadable file. Each case also makes `read_state` raise `BundleError`; the test asserts both from one parametrised table, so the two rules cannot drift.
- T-U3c: a checkpoint that `checkpoint_problem` rejects gives `INVALID` (`bad-checkpoint`).
- T-U4: marker with an empty key gives invalid (unknown origin).
- T-U5: a key but no marker gives invalid.
- T-U6: marker that is not JSON, has the wrong `schema`, is a directory, or is a symlink gives invalid, and the bytes are not echoed.
- T-U7: `write_marker` is atomic (no `.tmp` left behind) and records `seeded_by_run`.

## 11. Rollout and rollback

**Rollout**
1. This plan PR is merged by the owner.
2. Red tests commit, then the implementation commit, on `feat/71-state-cache`. CI goes green and the P9 jobs run.
3. The owner merges.
4. The owner dispatches `refresh.yml` with `seed_state=true` on main, before the next health run if Q2 picks "red".

6. Weekly refresh keeps going red with exit 3 until G2, which is expected and unchanged. Once G2 wires refresh, the first wired run classifies `SEEDED`, announces once, records and saves. Every later run classifies `PRESENT`.

**Rollback**
1. Revert the implementation PR. Refresh goes back to `--require-state` with no restore, which is the exit-2 red behaviour as today, so the fail-safe still holds.
2. Leftover cache entries are inert and evict after 7 days. They can be removed sooner with `gh cache delete <key>` from a machine with repository admin rights.
3. The marker and record formats are versioned (`v1`), so a later re-implementation does not read stale entries.

## 12. OPEN questions for the owner

1. **Where does the seed step live?**
   - (a) A `seed_state` boolean dispatch input and `seed` job in `refresh.yml`. **Proposed.** It inherits the `refresh` concurrency group, adds no workflow file and needs no change to the six-workflow list in `test_hosted_runner.py`. The trade-off is that `refresh.yml` gets a second job and two `if:` conditions.
   - (b) A separate `seed-state.yml`. This keeps `refresh.yml` single-purpose and the seed obvious in the Actions UI. It must repeat the key scheme and join the same concurrency group, and it is one more workflow to maintain and test.
   - (c) An automatic seed when the state is `ABSENT`. No manual step, but it recreates the silent "lost state equals first publish" path that #71 forbids. Not recommended.
2. **What does health do when the state is `ABSENT`?**
   - (a) Always red (exit 5). Strictest, but health goes red every night from merge until the seed dispatch.
   - (b) A warning while `REFRESH_WIRED` is False, red after. **Proposed.** It mirrors the existing exit-3 rule, but there is one more state to reason about.
   - (c) Health ignores the marker and keeps today's never-run logic. Smallest change, but health cannot tell eviction from "never ran" once refresh is wired.
   - Unchanged by review, with two notes. `INVALID` fails health under every option; Q2 covers only `ABSENT`. A cache outage that degrades to a miss (§9, outcome A) also classifies `ABSENT`, so under (b) an outage while unwired is a warning, not red. That is acceptable while nothing reads the state, and it turns red under (a) or once wired.
3. **Save after a failed run?**
   - (a) Save on `!cancelled()` when the state is not absent. **Proposed.** Keeps checkpoints a partly successful refresh wrote and refreshes the entry's 7-day clock.
   - (b) Save only on success. Simplest to reason about, but a failed wired refresh discards its checkpoints and redoes that work next run.
   - (c) `always()`, cancellations included. It can save between Announce and Record. That is harmless today because Record only advances after announce, but it widens the window.
   - Updated: (a) and (c) both depend on the `state_verify` step also running after a failure, so it now carries `if: ${{ !cancelled() }}` (T-W12). Under (b) the verify step can keep the default condition.
4. **Prune old cache entries?**
   - (a) No, rely on the 7-day eviction. **Proposed.** Entries are a few KB, and no `actions: write` is needed.
   - (b) A prune step (`gh cache delete` for all but the newest), which needs `actions: write` on the refresh job [D4]. This gives a tidy cache list, but widens the token's scope and adds custom machinery.
5. **What happens to a refresh dispatched on a non-default branch?**
   - (a) It restores main's state, never saves, and can still announce. Useful for testing, but an announcement from a branch is not recorded, so main announces the same bundle again.
   - (b) The refresh job refuses to run (`if:` default branch) for anything but dry runs. No stray announcements, but the full path cannot be exercised from a branch.
   - (c) As (a), with the announce and record steps also gated to the default branch. **Proposed.** Branch runs exercise restore, detect and classify without side effects. This adds one more `if:` condition to test.
6. **Where is the decision recorded?**
   - (a) A new ADR-017, "State persistence via actions/cache". **Proposed.** A clean record that ADR-016 can point to, at the cost of one more ADR to keep current.
   - (b) An amendment to ADR-016's Consequences section. Fewer documents, but it mixes two decisions in one ADR.
7. **How does a run prove its save landed?** (new, from review)
   - (a) Report `save-attempted-key` and let the next health run confirm it by restoring that key (T-R2 checks this once; every health summary shows it afterwards). **Proposed.** No new permission and no custom step. The cost is that a failed save is visible up to 24 hours later, and only as a stale `restored-key` plus the save step's warning.
   - (b) Add a post-save step: `gh cache list --key <key> --json key` that fails the job when the key is missing, and report `saved-key`. Same-run proof, but the refresh job needs `actions: read` and `GH_TOKEN`, and it adds custom verification on top of a vendor action, against the standard-CI/CD rule. A save that fails after Record has already announced, so a red job here cannot undo anything; it only alerts sooner.
