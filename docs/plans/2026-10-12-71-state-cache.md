## 1. Goal

Since ADR-016, the state that refresh and health keep under `~/.local/state/legal-corpus-ingester/` starts empty on every GitHub-hosted job. The goal is for that directory to survive from one run to the next through `actions/cache`. The design must never confuse "no state was restored" with "state says nothing changed" (the success-path defect class named in #71). It also needs an explicit seed step, so the first record can be written on purpose and the `--require-state` guard kept by the owner's ruling on PR #69 doesn't leave refresh red forever.

### Acceptance criteria

1. `refresh.yml` restores the state directory before any step reads it and saves it under a new, run-unique key after the record step. `health.yml` only restores it and never saves.
2. The reader reports one of three states, and the workflow log shows which one:
   - `absent`: cache miss or eviction. The run is red (exit 2, `EXIT_NO_STATE`, kept) and is never reported as "unchanged".
   - `seeded`: a seed marker exists but no bundle has been recorded yet. The first publish counts as a change and is announced exactly once.
   - `present`: the marker and a record both exist. The normal comparison runs.
3. A restored cache entry that has no marker, or a marker on a run where no cache entry was restored, is exit 1 (an untrusted store). It is not `absent`.
4. A seed path exists. It runs only on the default branch, refuses to seed over state it has restored, and saves a cache entry that the next refresh and health runs restore.
5. A save never writes an entry that would shadow good state. No save happens when the classification is `absent` or invalid, on a cancelled run, or from a ref other than the default branch.
6. Every state-touching job has a least-privilege `permissions:` block (`health.yml` has none today), and all state writers share one `concurrency:` group.
7. Red tests in §10 are committed first and fail for the stated reason; they turn green with the implementation; CI is green on the exact tip.
8. The ADR-016 "Consequences" paragraph and the `refresh.yml` comment on `--require-state` are updated, so neither says persistence is undecided. Which document records the decision is OPEN Q6.

## 3. Key scheme

```yaml
key:          ingester-state-v1-${{ github.ref_name }}-${{ github.run_id }}-${{ github.run_attempt }}
restore-keys: |
  ingester-state-v1-${{ github.ref_name }}-
  ingester-state-v1-${{ github.event.repository.default_branch }}-
path:         ~/.local/state/legal-corpus-ingester
```

The key has to be different on every save, because cache entries are immutable. GitHub's docs say: "You cannot change the contents of an existing cache. Instead, you can create a new cache with a new key" [D1]. The actions/cache tips page gives the same recipe: a key unique to each run, such as `github.run_id`, plus `restore-keys` to fetch the nearest entry [D4]. A constant key would be written once and then never change, which would freeze the first record forever. That is the failure #71 warns about.

- `run_id` makes the key unique per run. `run_attempt` makes a re-run of the same run unique too. Without it, a re-run would try to save an existing key, and [D3] does not document what that does.
- **The `restore-keys` prefix** fetches the newest entry: "If there are multiple partial matches for a restore key, the action returns the most recently created cache" [D1]. A partial match sets `cache-hit` to `false` and puts the restored key in `cache-matched-key` [D2]. So the reader is given `cache-matched-key`, never `cache-hit`.
- `ref_name` plus a fallback to the default branch: a run can restore caches from its own branch and from the default branch, but not the other way round. A cache created by a pull-request run is scoped to `refs/pull/.../merge` and can only be restored by re-runs of that PR [D1]. Saves are gated to the default branch (§5), so in practice every entry is `ingester-state-v1-main-…`. The first `restore-keys` line matches only on main. The second lets a branch dispatch read main's state without being able to write any.
- `v1` is a schema segment. A future change to the marker or record format bumps it to `v2`, so old entries can never be restored into new code.
- **The path must be the same literal string in both workflows.** The cache version is a hash of the compression method and the `path` [D5], so if `refresh.yml` and `health.yml` spell the path differently, health misses on every run. A test pins this (T-W3). `~` is supported in `path` (the README examples use `~/.npm`, `~/.cache/pip` [D5]). The `${XDG_STATE_HOME:-…}` shell form cannot be used in a `with:` input, so the steps pass explicit `--state-file` and `--state-dir` values derived from the same root, and `XDG_STATE_HOME` is never relied on.

## 4. State layout and reader states

```
~/.local/state/legal-corpus-ingester/
  store.json                    # NEW marker: {"schema": 1, "seeded_at": "<UTC ISO>", "seeded_by_run": "<run_id>"}
  last-published-bundle.json    # existing record (detect_bundle_change.py)
  state/<source>.checkpoint.json  # existing checkpoints (health_check.py, ingester status)
```

`classify(root, restored_key)` takes the matched key the workflow passes in (`--restored-key "${{ steps.restore.outputs.cache-matched-key }}"`, which is empty on a miss):

| `restored_key` | `store.json` | Result | detect (`--require-state`) | health_check |
|---|---|---|---|---|
| empty | missing | `ABSENT` (miss or eviction) | exit 2, nothing written to `GITHUB_OUTPUT`, `::error` naming the reseed procedure | exit 5 (or a warning while unwired, OPEN Q2) |
| empty | present | invalid: state of unknown origin | exit 1 | exit 4-class: fail |
| non-empty | missing | invalid: cache entry without a marker | exit 1 | fail |
| non-empty | present, no record | `SEEDED` | `changed=true`, `reason=first-record` | normal never-run rules |
| non-empty | present, record | `PRESENT` | normal compare | normal rules |
| any | unreadable, bad JSON, wrong schema | invalid | exit 1 (existing `BundleError` path) | fail |

Three properties follow. `ABSENT` can never be read as "unchanged". `SEEDED` is the only way a first publish gets announced, and it happens because someone seeded on purpose, not because state was lost. The cross-check against `restored_key` stops a stray directory on the runner (or a future self-hosted runner) from passing as restored state.

When no flag is given, the current behaviour stays the same (`test_without_the_flag_first_publish_is_still_a_change`). The new rules apply only under `--require-state` / `--restored-key`, which the workflows always pass (T-W4).

## 5. Order in `refresh.yml`, and whether to save on failure

1. `actions/checkout` (persist-credentials: false, as now)
2. `actions/cache/restore` (`id: state_restore`), with `key` and `restore-keys` from §3
3. Preflight, setup-python, Install (unchanged)
4. `python scripts/state_store.py check --restored-key … --github-output "$GITHUB_OUTPUT"` (`id: state_check`). It logs the state and matched key to `$GITHUB_STEP_SUMMARY`. Exit 2 or 1 stops the job here with a clear message, before refresh spends its fetch budget.
5. `ingester refresh --all` (exit 3 until G2, unchanged)
6. Detect (`--require-state --restored-key …`), then Announce, then Record (unchanged order; Record still runs only after a successful announce)
7. `scripts/state_store.py check` again (`id: state_verify`), so a corrupt record is never saved
8. `actions/cache/save`, with:
   ```yaml
   if: >-
     !cancelled()
     && github.ref == format('refs/heads/{0}', github.event.repository.default_branch)
     && steps.state_verify.outputs.state != ''
     && steps.state_verify.outputs.state != 'absent'
   with:
     key: ${{ steps.state_restore.outputs.cache-primary-key }}
   ```
9. Upload health report (unchanged)

**Proposed decision: save on failure, but not on cancellation** (`!cancelled()`, not `always()`). OPEN Q3 lists the alternatives.

- Saving after a failure is safe because the record is only ever advanced after a successful announce, and `write_state` / `CheckpointStore.save` replace files atomically. Whatever is on disk at step 8 is a consistent "last announced" view. Saving it unchanged just refreshes the entry's access time. The vendor documents this pattern: `actions/cache/save` with `always()` [D3].
- Skipping a save after a failure loses nothing that was announced. It does lose checkpoints a partly successful wired refresh wrote, so the next run starts from older checkpoints.
- Cancellation is excluded because a cancel can land between Announce and Record. Saving in that case gives a duplicate announcement next week, which is loud. Not saving gives the same result. `!cancelled()` keeps the rule simple.
- Saving when the state is `absent` would create an empty entry that is newer than the good one. `restore-keys` would then pick it [D1] and **shadow** the good state. The `state != 'absent'` and verify gates exist for exactly this reason.

`health.yml` order: checkout, restore (same `path`, same `restore-keys`, `key` set to a value that never matches such as `ingester-state-v1-read-${{ github.run_id }}`), setup-python, install, `health_check.py --state-dir <root>/state --restored-key …`, `ingester status`, upload. It has no save step. Health is the "low-trust" reader that [D1] says should use restore-only.

## 6. Eviction and its side effect

Entries "not accessed in over 7 days" are evicted, within a 10 GB repository cap by default [D1]. Refresh runs weekly (Sunday 03:00 UTC), right on that boundary. Health runs nightly and restores the newest entry, which counts as an access and keeps that entry alive. If health is disabled for more than 7 days and refresh does not run, the state is evicted. The next refresh then classifies `ABSENT`, goes red with exit 2, and the operator reseeds (§7). The cost is at most one duplicate announcement and never a silent miss. Each entry is a few KB, so the 10 GB cap is not a concern. Older entries age out on their own 7-day clock (OPEN Q4 covers active pruning).

## 7. The seed step

- **Who:** the owner, or an operator acting on the owner's instruction, by a manual `workflow_dispatch` on the default branch. It never runs automatically. An automatic seed when the state is `ABSENT` would recreate the silent "never run equals first publish" behaviour that #71 exists to prevent (OPEN Q1, option c).
- **When:** once, right after the implementation PR merges, and before the next 03:00 UTC health run if Q2 picks "red". After that, only to recover from an `ABSENT` red run (eviction, or a `v2` schema bump).
- **What:** restore (same key scheme). Then `state_store.py seed --restored-key …`, which refuses with exit 1 unless the state classifies `ABSENT`, so it cannot overwrite live state and cause a duplicate announcement. It then writes `store.json` and saves under `ingester-state-v1-main-<run_id>-<attempt>`.
- **Proposed placement (OPEN Q1, option a):** a `seed` job inside `refresh.yml`, selected by a boolean `workflow_dispatch` input `seed_state`. Its condition is `if: inputs.seed_state && github.ref == format('refs/heads/{0}', github.event.repository.default_branch)`, and the `refresh` job gets `if: ${{ !inputs.seed_state }}`. Both jobs sit under the workflow's existing `concurrency: refresh` group, so a seed can never race a refresh.
- **Check after seeding:** `gh cache list --key ingester-state-v1-` shows the new entry, and the next health run's summary reads `state=seeded`.

## 8. Concurrency and permissions

- **Concurrency:** keep `refresh.yml`'s workflow-level `group: refresh`, `cancel-in-progress: false`; the seed job inherits it because it lives in the same workflow (Q1a). If Q1 picks a separate workflow, that workflow must join the same group name. A single group allows one running run and one pending run; a third queued run replaces the pending one. With a weekly schedule plus manual dispatches, that is acceptable. `health.yml` needs no group because it never writes. A health run that restores while a refresh is saving gets the previous entry, which is consistent but one run old.
- **Permissions:** cache restore and save use the runner's Actions runtime token, not `GITHUB_TOKEN` scopes. The actions/cache README asks for no `permissions:` entry [D5], and "read-only" cache access degrades to a warning, never a failure [D5]. The implementer confirms this on the first dispatch, which is test T-R2. Resulting blocks:
  - `refresh.yml`: unchanged (`contents: read`, `issues: write`); the `seed` job sets `permissions: contents: read`.
  - `health.yml`: add `permissions: contents: read`. Today it has no block and inherits the repository default.
  - `actions: write` is needed only for `gh cache delete` [D4], which is OPEN Q4b.
- **Pinning:** `actions/cache/restore` and `actions/cache/save` are pinned by full SHA with a version comment, matching the other actions. The latest release on 2026-10-11 was `v6.1.0` → `55cc8345863c7cc4c66a329aec7e433d2d1c52a9` (`gh api repos/actions/cache/commits/v6.1.0`). The implementer re-checks this at implementation time.

## 9. Failure modes and observability

| Failure | Detected by | Result |
|---|---|---|
| Cache miss, eviction, or first run before a seed | `classify` gives `ABSENT` | refresh red with exit 2 and `::error` "state cache miss: no entry for prefix ingester-state-v1-…; reseed via …"; health exit 5 or a warning (Q2) |
| Restored entry with no marker | `classify` gives invalid | exit 1 |
| Corrupt record or checkpoint | existing `BundleError` / `checkpoint_problem` | exit 1 / 4 (unchanged) |
| `path` differs between workflows | T-W3 in CI; at runtime a miss classifies `ABSENT` | red, never silent |
| Cache service outage during restore | restore step succeeds with a miss [D2] | `ABSENT`, red |
| Cache service outage during save | the save step's own error or warning | the next run restores the previous entry. A second announcement of the same bundle is possible, and it is loud |
| Seed run while state exists | `seed` refuses (exit 1) | no overwrite |
| Branch dispatch | save gated to the default branch | branch runs never write state (Q5) |
| Cancelled between Announce and Record | `!cancelled()` gate | one duplicate announcement next run |

Observability: every run writes `state=<absent|seeded|present>`, `restored-key=<key or none>` and `saved-key=<key or skipped: reason>` to `$GITHUB_STEP_SUMMARY`. A skipped save says why, so a save that silently does nothing cannot happen. The health report gains one line naming the state.

## 11. Rollout and rollback

**Rollout**
1. This plan PR is merged by the owner.
2. Red tests commit, then the implementation commit, on `feat/71-state-cache`. CI goes green and the P9 jobs run.
3. The owner merges.
4. The owner dispatches `refresh.yml` with `seed_state=true` on main, before the next health run if Q2 picks "red".
5. T-R1 and T-R2 evidence is recorded.
6. Weekly refresh keeps going red with exit 3 until G2, which is expected and unchanged. Once G2 wires refresh, the first wired run classifies `SEEDED`, announces once, records and saves. Every later run classifies `PRESENT`.

**Rollback**
1. Revert the implementation PR. Refresh goes back to `--require-state` with no restore, which is the exit-2 red behaviour as today, so the fail-safe still holds.
2. Leftover cache entries are inert and evict after 7 days. They can be removed sooner with `gh cache delete <key>` from a machine with repository admin rights.
3. The marker and record formats are versioned (`v1`), so a later re-implementation does not read stale entries.

## 12. OPEN questions for the owner

1. **Where does the seed step live?**
   - (a) A `seed_state` boolean dispatch input and `seed` job in `refresh.yml`. **Proposed.** It inherits the `refresh` concurrency group, adds no workflow file and needs no change to the six-workflow list in `test_hosted_runner.py`. The trade-off is that `refresh.yml` gets a second job and two `if:` conditions.
   - (b) A separate `seed-state.yml`. This keeps `refresh.yml` single-purpose and the seed obvious in the Actions UI. It must repeat the key scheme and join the same concurrency group, and it is one more workflow to maintain and test.
   - (c) An automatic seed when the state is `ABSENT`. No manual step, but it recreates the silent "lost state equals first publish" path that #71 forbids. Not recommended.
2. **What does health do when the state is `ABSENT`?**
   - (a) Always red (exit 5). Strictest, but health goes red every night from merge until the seed dispatch.
   - (b) A warning while `REFRESH_WIRED` is False, red after. **Proposed.** It mirrors the existing exit-3 rule, but there is one more state to reason about.
   - (c) Health ignores the marker and keeps today's never-run logic. Smallest change, but health cannot tell eviction from "never ran" once refresh is wired.
3. **Save after a failed run?**
   - (a) Save on `!cancelled()` when the state is not absent. **Proposed.** Keeps checkpoints a partly successful refresh wrote and refreshes the entry's 7-day clock.
   - (b) Save only on success. Simplest to reason about, but a failed wired refresh discards its checkpoints and redoes that work next run.
   - (c) `always()`, cancellations included. It can save between Announce and Record. That is harmless today because Record only advances after announce, but it widens the window.
4. **Prune old cache entries?**
   - (a) No, rely on the 7-day eviction. **Proposed.** Entries are a few KB, and no `actions: write` is needed.
   - (b) A prune step (`gh cache delete` for all but the newest), which needs `actions: write` on the refresh job [D4]. This gives a tidy cache list, but widens the token's scope and adds custom machinery.
5. **What happens to a refresh dispatched on a non-default branch?**
   - (a) It restores main's state, never saves, and can still announce. Useful for testing, but an announcement from a branch is not recorded, so main announces the same bundle again.
   - (b) The refresh job refuses to run (`if:` default branch) for anything but dry runs. No stray announcements, but the full path cannot be exercised from a branch.
   - (c) As (a), with the announce and record steps also gated to the default branch. **Proposed.** Branch runs exercise restore, detect and classify without side effects. This adds one more `if:` condition to test.
6. **Where is the decision recorded?**
   - (a) A new ADR-017, "State persistence via actions/cache". **Proposed.** A clean record that ADR-016 can point to, at the cost of one more ADR to keep current.
   - (b) An amendment to ADR-016's Consequences section. Fewer documents, but it mixes two decisions in one ADR.
